## 9. 1셀 요청 경로가 cuPHY를 멈추던 원인 (2026-11-02 08:50 KST)

증상: 1셀 KPI 런에서 첫 요청 직후부터 매 요청마다 L1이 recovery에 들어가고(k1_26l_av4: 358건 성공했지만 recovery 761줄·PrePrepare 오류 628건 — "유효" 결과가 아님), 26x는 3초 뒤 `task_function_dl_aggr.cpp:131` FATAL로 죽음. 테넌트 자체는 정상 응답(26x 39 ms).

제외한 가설: 요청 경로의 cudaFree/버퍼 재할당(아레나·고정 RGB 버퍼로 제거, 변화 없음), 디코더 워밍업(변화 없음), 컨텍스트 락(독립 실행에 cuPHY 역할 스레드 추가: 83건 동안 최대 지연 1.3 ms, 재현 안 됨), 레거시 기본 스트림(cuPHY 스트림이 모두 non-blocking).

이분법(bisect12, 각 1셀 4 req/s 26x): 추론 생략·디코드만 → 84건/20 s 무사 후 recovery 1회·FATAL; 디코드 생략·추론만 → 첫 요청 1 s 뒤부터 recovery 251줄, 6 s 뒤 FATAL. 추론(녹색 컨텍스트 파티션)이 주범, 디코드(프라이머리 스트림 커널)는 드문 부차 원인.

배치 유도(cuphydriver context.cpp의 split 순서; 결과 = 앞쪽 SM, 나머지 = 뒤쪽 SM, 8셀에서 검증된 사실과 일치):
- UL order 컨텍스트 = yaml PUSCH 컨텍스트 여집합의 **마지막** order개 SM. 8셀(yaml PUSCH 100, order 8): 여집합 [0,32) → order [24,32) = PDSCH 40 prefix 안 → 테넌트 틈 [40,…)과 겹치지 않음(8셀 런이 깨끗했던 이유).
- 1셀(사다리 16‥56 → yaml 60, order 20→24): 여집합 [0,72) → order **[48,72)** → 테넌트 틈 [24,112) 안. class 80 [24,104)·class 56 [24,80) 모두 order 커널 SM을 덮음 → YOLO 블록이 상주하는 동안 패킷 대기 order 커널이 뜨지 못함 → "AGGR waiting for PHY channels", "No available UL input buffers", PrePrepare 대기 → recovery.
- 테넌트의 틈 구성은 PDSCH prefix와 PUSCH 나머지만 제외하고 고정 컨텍스트는 "prefix 안"으로 가정했다(8셀에서만 검증, §8 미검증 항목). 1셀에서 그 가정이 깨졌다.
