E2E scenario preparation - what was measured with the whole GPU (MIG off), 2026-10-04 22:30 - 10-05 14:42 KST
==========================================================================================================
Goal: find the scenario (traffic mix, YOLO model, baseline definition) in which our approach (MPS sharing +
estimator + scheduler + model selection) cuts the UE-to-UE latency of a 4K inference request by >= 10 % against
static MIG (cuPHY in 4g.48gb, tenant in 3g.48gb). Everything here ran without a UE. The MIG-side runs
(e2e_prep/e2e_prep_mig.sh: tenant in 3g, full-stack load ladder in 4g) are NOT done yet, so every "MIG 3g"
number below is an estimate from the cap-50 (66 SM) tenant-alone runs and is marked (est.).

Conditions: 16 cells, cubb_gpu_test_bench DDDSUUDDDD (lowest = c16_L1, highest = c16_L4), 2-min runs (~1.8e4 slots,
p99 only, provisional), tenant = TensorRT FP16 YOLO26 n/s/x at a 1280x1280 input (4x the FLOPs of 640),
batch 1 = whole 4K frame letterboxed, batch 8 = "tiled" request (6 native 1280 crops + global views).
Runs: sweep profiles c16_capgrid_1280 (56), c16_openloop_1280 (12), c16_ratelimit_1280(_b8) (8), e2e/gh200_segment.sh
(real pipeline, batch 1 and tiled), fullstack/ladder_runs.sh ref (4). Driver log: driver_mig_off.log.

Incident: the host went down uncleanly at 00:45:59 on 10-05, 13 s into the first run of 26x-1280 cap 100 next to
the 16-cell L4 bench (no shutdown record, no panic/Xid in syslog, pstore empty; GPU 606-617 W, 75 C, below the
661-667 W of earlier runs). After the restart the same combination and heavier ones (26x b8 cap 100, 684 W, 83 C)
ran without incident, so the combination does not reproduce it. (The 19:19 reboot the same day was a clean one by
another user.)

8. Reading
   - AI side: with cuPHY protected, the shared GPU is not faster than an isolated 3g instance for the same model
     (26x b1: 6.4 ms lowest / 13.9 ms highest vs ~7 ms (est.); tiled 26x: 68 ms / no safe cap vs ~42 ms (est.)).
     Raising the cap buys speed only by breaking cuPHY deadlines.
   - A >= 10 % E2E gain therefore has to come from (a) the RAN side - cuPHY keeps all 132 SMs, so the last PUSCH of
     the upload completes 0.6-1.3 ms earlier than in MIG 4g at 59c (heavier loads to be measured), and/or
     (b) model selection against a baseline whose model is fixed: baseline 26x vs ours 26n at the highest load is
     about -11 % (batch 1) / -35 % (tiled) of an estimated 48 / 87 ms E2E, and ~0 % or worse if the baseline's
     fixed model is 26s or 26n. (b) trades accuracy and must be reported with it.
   - Open: MIG 3g latencies of the 1280 engines, the MIG 4g full-stack ladder, upload time with a real UE,
     26n tiled below cap 30, GPU-side NMS.
